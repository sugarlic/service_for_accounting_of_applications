# Application Service

Небольшой внутренний сервис для учёта заявок.

Сервис позволяет создавать заявки, просматривать их, фильтровать по статусу и менять статус через простой веб-интерфейс.

Также реализован API для интеграции с внешней CRM-системой.

## Возможности

- создание заявки;
- просмотр списка заявок;
- фильтрация заявок по статусу;
- изменение статуса заявки;
- хранение данных в PostgreSQL;
- простой веб-интерфейс;
- API для интеграции с внешней CRM;
- API-key для ограничения доступа к интеграционному API;
- автоматический запуск миграций при старте приложения;
- запуск приложения и PostgreSQL через Docker Compose.

### Статусы заявок

Поддерживаются следующие статусы:

| Статус | Значение в API |
|---|---|
| Новая | `new` |
| В работе | `in_progress` |
| Успешно | `success` |
| Отказ | `rejected` |

Новая заявка всегда создаётся со статусом `new`.

## Архитектура

Backend разделён на несколько слоёв:

```text
HTTP Handler
     ↓
   Service
     ↓
 Repository
     ↓
 PostgreSQL
```

### Handler

Отвечает за HTTP:

- получение и валидацию входных параметров;
- преобразование JSON;
- вызов service;
- формирование HTTP-ответов.

### Service

Содержит бизнес-логику приложения:

- проверку обязательных полей;
- проверку статусов;
- создание заявок;
- изменение статуса;
- получение заявок.

### Repository

Отвечает только за взаимодействие с PostgreSQL.

Такое разделение позволяет не смешивать HTTP, бизнес-логику и работу с базой данных.

## Запуск

Для запуска необходимы:

- Docker
- Docker Compose

Клонировать репозиторий:

```bash
git clone <repository-url>
cd <repository-directory>
```

Собрать и запустить приложение:

```bash
docker compose up -d --build
```

После запуска веб-интерфейс доступен по адресу:

```text
http://localhost:8080
```

При старте приложения миграции PostgreSQL применяются автоматически.

### Остановка

```bash
docker compose down
```

### Просмотр логов

```bash
docker compose logs -f app
```

## Внутренний API

### Создание заявки

```http
POST /admin/applications
```

Пример:

```json
{
  "name": "Иван Иванов",
  "phone": "+79991234567",
  "comment": "Интересует консультация",
  "source": "website"
}
```

Статус новой заявки устанавливается сервером автоматически:

```text
new
```

### Получение списка заявок

```http
GET /admin/applications
```

Фильтрация по статусу:

```http
GET /admin/applications?status=in_progress
```

Допустимые значения:

```text
new
in_progress
success
rejected
```

### Получение заявки

```http
GET /admin/applications/{id}
```

### Изменение статуса

```http
PATCH /admin/applications/{id}/status
```

Пример:

```json
{
  "status": "in_progress"
}
```

## Интеграция с внешней CRM

Для внешней системы выделен отдельный API resource:

```text
/api/v1/applications
```

Один URL поддерживает две операции посредством HTTP-методов:

```http
POST /api/v1/applications
GET /api/v1/applications
```

`POST` создаёт новую заявку, `GET` возвращает список заявок.

Это позволяет использовать один REST-ресурс для работы с заявками без создания отдельных URL для каждой операции.

### Авторизация

Для демонстрации организации внешней интеграции используется простой API-key.

Ключ передаётся в заголовке:

```http
X-API-Key: test-api-key
```

Полноценная система авторизации намеренно не реализовывалась, так как она не требуется в рамках задания.

### Создание заявки из CRM

```http
POST /api/v1/applications
X-API-Key: test-api-key
Content-Type: application/json
```

```json
{
  "name": "Иван Иванов",
  "phone": "+79991234567",
  "comment": "Заявка из CRM",
  "source": "crm"
}
```

### Получение заявок из CRM

```http
GET /api/v1/applications
X-API-Key: test-api-key
```

Для внутреннего и внешнего API используются разные HTTP handlers, но одна бизнес-логика приложения.

Это позволяет в дальнейшем независимо изменять внешний API, не дублируя основную логику работы с заявками.

## Работа с базой данных

В качестве базы данных используется PostgreSQL.

Основная таблица:

```text
applications
```

Для идентификаторов заявок используются UUID.

Статус хранится как строковое значение и дополнительно ограничен на уровне PostgreSQL через `CHECK`.

Для часто используемых запросов созданы индексы по:

- `status`;
- `created_at`;
- `(status, created_at)`.

Миграции встроены в Go-приложение через `embed` и автоматически применяются при его запуске.

## Основные технические решения

### PostgreSQL

PostgreSQL выбран как надёжная реляционная БД, хорошо подходящая для структурированных данных заявок.

### UUID

Для идентификаторов используются UUID. Это позволяет генерировать независимые идентификаторы и не раскрывать последовательность создания записей через API.

### Статусы

Статусы представлены строковыми значениями:

```text
new
in_progress
success
rejected
```

Допустимые значения проверяются как в приложении, так и ограничением `CHECK` в PostgreSQL.

### Источник заявки

Поле `source` оставлено строковым.

Для текущего задания нет необходимости создавать отдельный справочник источников. При появлении фиксированного набора источников его можно вынести в отдельную сущность.

### Миграции

SQL-миграции встроены в бинарный файл приложения и выполняются при старте.

Благодаря этому для запуска проекта через Docker не требуется отдельно запускать migration container или устанавливать CLI для миграций.

### Разделение внутреннего и интеграционного API

Внутренний интерфейс и CRM API имеют разные handlers, но используют один service.

Это позволяет избежать дублирования бизнес-логики и одновременно сохранить возможность независимо развивать контракты API.
